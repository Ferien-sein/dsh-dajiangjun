# 大管家 · 能力清单与分期方案

> 依据：`https://github.com/kira905/ops-handoff-design` 十一份方法论文档（v1.11，2026-09-28 双端发布）
> 落点环境：DeepSeek Harness **0.2.0-rc.2**（本机 Electron 桌面版，profile `desktop`）
> 本文档性质：**决策稿**。用途是让所有者挑 v1 做哪一条，不是设计稿。挑完之后另写设计稿。

## 0. 结论先行

**① 方法论里有大量工作，DSH 已经替我们做掉了。**
文档 10 花了整篇篇幅去反推"会话到底是不是被打断"（尾部新→旧折叠、补写收尾标记盖住真尾巴、38/38 落回合边界验证……），因为那套系统的日志里没有这个信息。DSH 有：`turn/end` 的 `TurnEndReason` 里直接有 `{kind:'interrupted'}` 和 `{kind:'aborted'}`，会话列表里直接有 `running` 布尔。**这一整块判据在本机不需要重建。**

**② 方法论的"✅ 已在生产"大部分在本机不存在。**
那套体系的生态由 6 个组件仓支撑（会话归档 / 会话标题实时刷新 / 只读生态面板 / 诊断取证工具组 / 自维护任务看板 / 急救台）。本机 profile 只装了 `dsh-better-sidebar`、`dsh-cost-meter`、`dsh-deepseek-web-login`、`dsh-plugin-notify-sound`、`dshmarket`、`dsh-tui`——**上面 6 个一个都没有**。所以文档里凡是"复用任务账本""面板已有一键处理""归档插件已全自动"这类句子，在本机都是**从零开始**。

**③ 有一块原理上做不了，不该硬凑。**
03 的"角色化班底"（五执行角色 + 内核 = 多常驻进程）不可实现，硬理由：**账本 `ledger-v2.lock` 是进程独占锁，同一主目录不能跑两实例**。跨机那几项（跨机样本并集、多机交接、云中继）也是"实测就是 2 台机 + 一台云主机"才能做的事。

**④ 按 ponytail 的梯子，v1 应该只做一条。**
这一点方法论自己也是这么说的——文档 02 的「MVP 砍单线」原文：**"只做一条 = P0"**、**"半成品一律不进生产"**。所以下面 §4 给的是"先做哪一条"的选择题，不是"一次做四期"的路线图。

## 1. 砍单清单：DSH 原生已覆盖，不要重造

| 方法论里的机制 | 出处 | DSH 原生替代 | 结论 |
|---|---|---|---|
| 会话"被打断"的尾部折叠判据、补写标记透明跳过、未知类型禁止前翻 | 10 | `SessionEventMap['turn/end']` 的 `reason.kind ∈ {completed, aborted, blocked, error, max-tokens, interrupted, forked}` | **砍掉整块**，直接读 `reason` |
| "这个会话还在跑吗" | 10, 02 | `ctx.sessionController.list()` → `SessionSummary.running` | 砍掉 |
| 手动维护会话标题前缀状态轴/接力轴、分层解析修法、≤59B 字节预算分配 | 09 | `ctx.sessionTitle.rename()` 是**钉住**语义（写 `session/title` 事件），且本机**不存在任何前缀重写层**（已核实 `dsh-session-title` 全文无剥离/分层解析）——标题不会被系统自动改写，谁写就是谁写的 | **砍掉标题机**，只用一个写标题的函数 |
| 自己解析多帧 zstd 会话日志来扫错误签名 / token 用量 | 02 P4, 05 | 实时侧：`session/event` 总线 + `tools/result` 事件；`assistant/message.data.usage` 直接给 `TokenUsage` | 增量可做，**历史回溯不可做**（见 §2） |
| 自建"卡片/账本"抽象再做假完成判定 | 10 | 无对应物——本机没有任何任务看板 | **砍掉卡片部分**，doc 10 只留会话侧 |
| 写自己的设置页面 | 02, 07 | 第三方**不能**注册设置命名空间：`ctx.settings.register()` 在 0.2.0-rc.2 **不存在**（全 asar 零命中；`notify-sound` 里那行是死代码）。第三方命名空间 = 插件自己的 `Config` schema | 用 `Config` + profile patch |
| 自建告警推送通道 | 02 P2 | `ctx.approval.request()` 可请求一次人工批准；`ctx.slots` 90 个槽位可挂 UI | 视需求再说 |

## 4. 分期方案

### S0 · 地基（**无论 v1 选哪条都要先做**）

不是一条能力，是三块所有东西都要踩的地板。**这也是 ponytail 的第 2 级：这些是已存在的模式，别重写。**

1. **审计流水**：`append-only JSONL + prevHash 哈希链`（02 §5.2）。定位必须写对——**防损坏 + 便于追溯**，不宣称"不可抵赖"。
2. **状态文件契约**：原子写（写临时文件 → `fs.rename` 覆盖，Windows 上失败要重试 3 次，**绝不退化为直接写目标**）+ 单例 tick 锁（`flag:'wx'` 原子创建，禁止先 `existsSync` 再写）+ `updateJson` 唯一入口。
3. **开关读取 + 动作注册表**：四级 kill switch，读不到按已降级（fail-safe）；动作注册表是 D5"未实现不许先登记"的载体。

工作量：**S**（1 个工作会话）。产出：共享模块 + 契约测试。没有用户可见功能，但省掉它后面每条能力都要各写一遍。

### S1 · 选一条完整能力

方法论自己的 MVP 砍单线要求"只做一条、半成品不进生产"。三条候选（都做了 §3 的可行性核实）：

| 选项 | 内容 | 工作量 | 为什么选它 | 为什么别选 |
|---|---|---|---|---|
| **A. 只读面板** | 06 的显示纪律 + 03 的日报段：一块只回答"今天怎么样、哪些东西静默坏了"的只读面板 | S0 + **M** | 唯一"给你看"的选项；三档取值纪律 + 缺数据夹具是**可以验收**的硬指标；ponytail 友好（只读、无副作用、砍掉 56% 死重） | 要同时写 host 和 client 两半，client 必须是已构建产物；且本机没有"生态面板组件"可复用，资产总览这一块暂时没数据源 |
| **B. 会话接力** | 09 精简版：写档 → 建会话 → 改名 → 投递 → 回写档头；**砍掉**标题三轴/工单改绑/无人值守通道 | S0 + **M** | 直接解决我自己最痛的问题（撞上下文上限）；5 件宿主能力已核实**有 4 件**；砍掉标题机后体量掉一大截 | 闸门有 12 道（方法论要求每条闸都有判据+动作+审计行+退出码+可见位置）；无人值守触发面依赖"工单执行会话"这个本机不存在的概念 |
| **C. 写入守门** | 02 P5 的 A 层拦截（`fs/write-intent` 抛 `FsError`）+ B 层写后审计回滚 | S0 + **M** | 代码量最小、纯确定性、0 token；防的是"把自己写坏"这类最难恢复的事故 | 方法论**自己论证过 A 层实际防护 ≈ 0**（事件门只给路径不给内容）；真正的防线是 B 层 + 磁盘 watcher，那就不是小活了 |

**我的推荐：A 或 B。** 如果"你能用的插件"里的"你"指**我（agent）**，选 **B**；如果指**所有者**，选 **A**。C 的性价比最低——它自己都承认第一层拦不住。

### S2 · 观测期（方法论强制，不可跳过）

- 窗口 ≥3 个自然日（含 1 工作日 + 1 周末）
- 只开：告警巡检（只盯人）+ 写入审计（A 层拦截 + B 层只告警不回滚）+ 人主动请求路径

- 放行门槛：误报率 <5%，且**累计告警 ≥50 条**（样本不足不得放行）；未 ack >4h 计"疑似误报"单列，疑似占比 >10% 同样不放行

## 6. 待验证假设（进插件的假设登记表）

| # | 假设 | 验证方式 | 失败退路 |
|---|---|---|---|
| A1 | 第三方 client 插件能读到自己的 `Config` 命名空间值 | 写最小 client 半体，读自己的设置 | 退回 `localStorage`（`notify-sound` 的老路） |
| A2 | `shell.overlay` 槽位能稳定承载一块常驻面板且不与在售 UI 冲突 | 最小注册 + 目视检查 | 退到 `settings.section`（整页 tab） |
| A3 | `fs/write-intent` 抛 `FsError` 不拖慢正常写入路径（P95 < 5 ms） | 加路径延迟预算 + 压测 | 只拦保护区白名单，非全量监听 |
| A4 | `sessionController.prompt(mode:'queue')` 投递到新会话后，新会话能自动开工 | 隔离环境真跑一条链（含失败注入） | 降级为"写档 + 提示所有者手动接手" |
| A5 | `turn/end.reason` 在全部中断路径上都可靠落盘（含强杀） | 构造强杀 + 重启场景，核对事件流 | 退回"活跃判定 = mtime + 尾部事件白名单" |
| A6 | profile patch 里 `- insert:` 的第三方行在 Electron 宿主下能热加载生效 | 装最小插件 → 刷新页面 → 看是否生效 | 重启宿主（但 boot 全有或全无，**必须先在隔离 profile 验**） |

### spike 结果（S1 前置）

**假设 A4「投递后新会话能否自己开工」→ 已验证成立，证据级别：源码级。**

链路（读自本机 `app.asar` 内 0.2.0-rc.2 的实际发布源码）：

```
sessionController.create(request)         → agents.ensureSession(sessionId, cwd, adopt, agentPreset)
sessionController.prompt({…mode:'queue'}) → resolveAgent(sessionId)   // 冷代理按需恢复
                                          → agent.followup(message)
                                          → send(message, 'next-turn', true)   // wakeup = true
                                          → wakeDriver()  → phase='running' → kick()
```

关键证据行：
- `dsh-agent-loop/lib/index.js:806` — `followup(input) { this.send(input, "next-turn", true) }`
- `dsh-agent-loop/lib/index.js:800-804` — `send()` 内 `if (wakeup) this.wakeDriver(wakingAfterAbort)`
- `dsh-agent-loop/lib/index.js:854-868` — `wakeDriver()` 在 idle 时直接 `setPhase({kind:'running'})` 并 `kick()`，**无"等人确认"中间态**
- `dsh-api-session-controller/lib/index.js:882-883` — `mode==='steer' ? agent.steer() : agent.followup()`
- `dsh-api-session-controller/lib/index.js:854` — prompt 先 `resolveAgent()`，能把冷代理恢复成活
- `dsh-api-session-controller/lib/index.js:937` 注释 — "restoring an ordinary cold Agent when needed"

**顺带确认的三兄弟语义**：`followup` / `steer` 均 `wakeup=true`；**只有 `inject` 是 `wakeup=false`**（塞进去但不叫醒）。选投递模式时别选错。

**未做的部分（照实登记）**：没有端到端实跑。阻断原因——宿主 HTTP 需 GUI 令牌，`~/.dsh/web-login` 是 Edge 传输配置目录、取不到可复用凭证；要实跑须先写插件 + 建隔离 profile + 拉起一套。按文档 07 的三级证据序，本机发布物源码属第二级，足以支撑架构选型；**实跑留到实现阶段**（文档 09 本就强制要求"隔离环境真跑一条链（含失败注入）"才许上生产）。

**残留风险**：`agents.ensureSession()` 内部究竟只建会话记录还是连带挂上活代理，未逐行确认；但 `resolveAgent` 的冷恢复路径 + `updateQueue` 的注释都指向"按需恢复"是受支持的正常路径。风险低，且与 A4 结论方向一致。

## 7. 装插件这件事本身的注意事项

- 装法：`dsh plugin --profile desktop add <包>`（**已实测 CLI 可以操作 desktop profile**）
- 加载：包的 `dsh.bundle.patch` → `cordis.patch.yml` → `- insert: [{id, name}]`
- **DSH 启动是全有或全无**：一个插件加载失败整个进程起不来，GUI 也跟着挂。所以：
  1. 先在**隔离 profile**（如 `--from-default-profile web` 建一个）里跑通，再进 `desktop`
  2. 进 desktop 前，先确认 `~/.dsh/profiles/desktop/cordis.patch.yml` 有可回退的备份（本机已有 `.bak-*` 的先例）
  3. 插件行写进 patch 层，禁用就是 `disabled: true`，**不要删文件**
- peer 依赖：`@deepseek-ai/cordis: ~4.0.4`、`@deepseek-ai/schemastery: ~3.18.4`，用到哪个服务再 peer 那个 `@deepseek-ai/dsh-*@0.2.0-rc.2`
- 客户端半体必须是**已构建产物**（宿主直接 serve，没有转译步骤）
