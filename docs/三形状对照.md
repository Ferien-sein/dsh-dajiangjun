# 三种形状 · 半页对照

- 日期：2026-10-07
- 性质：**决策稿**。用途是让所有者挑一条，不是设计稿。挑完之后按 brainstorming 的架构路径另写设计稿。
- 上游：本文档回复的是"开发侧流程 + 运行期纪律 + 多子智能体协同"这个笼统设想该落成什么形状。

## 0. 三种形状共享的部分（不因选择而变）

三条都是同一个设想的切面，下面这部分**任何一条都要做**：

| 共享件 | 内容 |
|---|---|
| **判据归位** | 开发和运行两套流程对"做完"的口径必须一致。运行期判据（判据 + 动作 + 审计行 + 退出码 + 可见位置）里，**代码能验的那部分**进闸门，**只能人判的那部分**进 skill。两者不许各写一份。 |
| **裁决权唯一** | 计划持有者（协调会话）独占裁决权；子代理只准"报告 + 提问"，不准自行改口径。superpowers 的 `Ruling` 制度保留，但只在协调者一层产生。 |
| **证据归属** | 每个派发出去的任务在**派发时**就带可执行验收命令；交回时必须带原始输出。协调者只认输出，不认总结。 |
| **风险分档** | 可逆动作走"继续"（superpowers 腔），不可逆动作走"停下等批准"（ops-handoff 07/11 腔）。**复用 03 R9 那张表，不造第二张。** |

## 1. 形状 A · 省上下文为主

**做什么。** 目标是主会话不被长任务撑爆。协调会话读计划、逐条派发，一次只有一个写者。子代理按 brief 干活、回报告、由协调者验收。接力器只负责一件事：**协调会话自己撞上限时交班**。

**代码要动什么。**
- 不动现有 `lib/` 三文件，不改闸门、不改审计链、不改锁。
- 新增一个**任务卡契约**（brief 模板的字段约定 + 派发时校验：验收命令必填、允许写的文件清单必填）。可以只是一个 skill + 一组断言。
- 可选：`steward_relay` 的档头多记一个字段 `已完成任务: T1..Tn`，让接力后的会话知道计划走到哪。

**砍什么。**
- 不做工单/工作流键、不做文件级锁、不做 worktree、不做并行派发工具、"派活"完全靠模型自己按 skill 手动调用。
- 不做任务队列、不做状态机——进度就在计划文件的复选框和 SDD 台账里。

**superpowers 怎么用。** 这是 `subagent-driven-development` 的**原样使用**，几乎不用改：
- Setup（worktree/台账/预检）→ 每任务一个实现者 → 每题审一次 → 全分支终审 → `finishing-a-development-branch`。
- 唯一要加的纪律：派发 brief 时强制带上"验收命令 + 允许写文件清单"，回来时强制收原始输出。
- `Ruling` 只由协调者产生（现状已经是这样）。

**任务条数估算。** **3–5 条**（都不是新子系统）：① 任务卡契约 + 派发自检；② 派发/验收的 skill 包（含"只认输出不认总结"的措辞）；③ 接力档头加"已完成任务"字段（可选，1 条）；④ 用现有 10 条任务做一次回归验证。

**最大的坑。** 它**没有强制力**。"一次一个写者""必带验收命令"全靠协调者自觉——模型在压力下会跳过。而且协调者自己也会被上下文撑爆，那时还是得靠接力器。

**什么时候选它。** 你主要痛的是"长任务把主会话撑爆"，且能接受串行。

## 2. 形状 B · 抢吞吐为主

**做什么。** 真并行跑多条工作流。协调器从计划里挑出无依赖的任务，派给 M 条工作流，每条一个会话 + 一个身份；文件互不重叠的才允许并行，重叠的排队。

**代码要动什么。**
- 接力器扩成**派活器**：`steward_relay` → `steward_dispatch`。
- 新增**工单键**：这是现在明确不存在的（设计稿 N1 已核实 `SessionHeader`/`SessionSummary` 无工单字段）→ 必须自建 `任务id ↔ 会话id` 映射，存自己的状态文件。
- 审计行加 `workstream` 键；哈希链仍是单链（单实例），但**按 workstream 分段可查**。
- **文件级写锁**：以"允许写的文件清单"为键，抢不到就排队不并行。
- 锁粒度从"源会话单飞"降到"文件/目录"。
- 可选：每条工作流一个 `git worktree`（你仓里 Ruling 5 已定过"不做 worktree"，这里要重新裁决一次）。

**砍什么。**
- 不建中心队列服务、不建调度守护进程、不做优先级抢占。
- 不做跨机（一台机）。
- 不做"自动生成任务分解"——分解仍由 planning 阶段和人确认，B 只负责**派发与回收**。

**superpowers 怎么用。** `subagent-driven-development` 要**动刀**：它的"每题一实现者 + 一评审"是串行设计，B 要在其上叠一个轻量调度循环——`取任务 → 派发 → 回收证据 → 评审 → 下一个`，并显式限制"同一时刻的写者数"。`dispatching-parallel-agents` 的禁令（*"Shared state: Agents would interfere"*）是 B 的红线，靠文件锁满足它。

**任务条数估算。** **8–12 条**（这是新子系统）：① 工单键与映射存储；② 审计行加 workstream + 分段查询；③ 文件级锁；④ dispatch 工具（派发/回收/超时）；⑤ 单飞 → 多飞的状态模型；⑥ 半完成态的批量处置；⑦ 调度循环 skill；⑧ 死锁与饥饿检测；⑨ worktree 裁决与实现（若选）；⑩–⑫ 端到端并发验证。

**最大的坑。** 三个：**(a)** 并发写文件是**只能串行**的，B 的并行度上限由"文件不重叠"决定，实践中往往只有 2–3 条流；**(b)** 一个 worktree 一份依赖树，宿主跑不动多实例（账本独占锁 + 单主目录单实例）——所以"并行"只能在**子会话层**，不能在宿主层；**(c)** 假完成从 1 份变 N 份，验收主体必须显式定义，否则并行越多越不可信。

**什么时候选它。** 你的瓶颈是"任务多到串行做不完"，且愿意接受并行度其实只有 2–3。

## 3. 形状 C · 沉淀判据为主

**做什么。** 不解决速度问题，解决**口径问题**：把"哪些步骤能靠成熟案例直接生成、哪些必须人确认"固化成可执行的判据表和 skill 包，让下次提模糊要求时，分档是**照表判**而不是**凭感觉**。

**代码要动什么。**
- 几乎不动 `lib/`。
- 新增**动作登记表**：列 = 动作 / 风险级 / 是否可直接生成 / 必须确认什么 / 回执形式。这是 07 那张表的最小版。
- 关键闭环：**大管家的运行期闸门要能读这张表**。否则它是一张纸，不是判据——这是 C 唯一一处真正的代码改动（表 → 闸门读取 + fail-closed）。

**砍什么。**
- 砍一切"编排脚本"（不产新能力）。
- 砍统计门槛：07 的 `1−0.05^(1/n)` 在 n=50 时也只有 5.8% 误报上界，你一个人攒不出样本 → **自动化放行一律"先问"档**，等真有样本再谈。
- 砍审计链改动、砍并发改动（C 不碰单进程）。

**superpowers 怎么用。** 蒸馏成**项目级 skill**：`brainstorming` 的分类（spike/bounded/architectural）→ 你要的"必须确认 / 可直接生成"两档的映射。做法是把 `brainstorming` 的路径分类 + `writing-plans` 的`全局约束/Interfaces(Consumes/Produces)/每任务 Files 清单`三节当判据。**这三节是"可直接生成"的判据：能写全就是熟路，写不全就是必须确认。**

**任务条数估算。** **3 条**：① 判据表 + 动作登记表（数据，不是代码）；② 项目级 skill 包（`using-superpowers` 风格的入口 + 三张表 + 一页速查卡）；③ 运行期闸门读表 + fail-closed 断言（唯一代码）。

**怎么知道它成了。** 找一个**已知答案的样本**验证：大管家自己的能力清单里有 26 条可直接生成 / 一批必须确认——判据表能不能从零复现同一套分档。**判据写完之后，用另一个子代理从零扫一遍来反证。**（这是"前提实证"的用法：不是我相信自己对，是让独立的证据来判。）

**最大的坑。** 它对人**约束最弱**——表放在那里没人读就等于没有。寿命也短：项目一停更就僵化。

**什么时候选它。** 你的项目已经能跑、只是每次开新活都要重新想一遍"哪些能自动生成"。

## 4. 三张对照

| | **A 省上下文** | **B 抢吞吐** | **C 沉淀判据** |
|---|---|---|---|
| 一句话 | 串行派活，主会话别爆 | 并行跑多条工作流 | 把分档固化成表 |
| 动 `lib/` 吗 | 不动 | 大动（派活器 + 工单键 + 文件锁） | 只动闸门读表 |
| 新子系统 | 无 | 有（工单键/文件锁/调度） | 无 |
| 新概念 | 任务卡契约 | workstream、文件级锁、半完成批处理 | 动作登记表 |
| 任务条数 | 3–5 | 8–12 | 3 |
| 依赖 | 无 | worktree 裁决、并发验证 | 现有 11 份文档当样本 |
| 上限 | 一个写者，串行 | 并发度 ≈ 文件不重叠宽度（常 2–3） | 不提升任何速度 |
| 强制力 | 弱（靠自觉） | 中（靠锁） | 弱（靠人读表） |
| 主要风险 | 退化成"随手丢给子代理" | 假完成 ×N、验证主体缺失、死锁 | 表僵化、无人读 |
| 和 superpowers | 原样用 | 要动刀 + 新增调度循环 | 蒸馏成 skill |
| 和 ops-handoff | 只留运行期判据 | 用 03 R9 / 07 分档 | 是 07 的判据化 |

## 5. 选择判据（三条互斥的痛点）

- **痛在"长任务把主会话撑爆"** → **A**。改版补两个函数，能直接长在现有大管家之上。
- **痛在"任务多到串行做不完"** → **B**。这是开一个新项目，按架构级重新走一遍设计。
- **痛在"每次开新活都要重新想哪些能自动生成"** → **C**。重心在 skill 包与判据表，代码基本不加。

**可叠加顺序**（若都不想做选择）：**C → A → B**。C 是把口径写下来，任何后续形状都需要它；A 是建立在 C 之上的执行方式；B 只有在 A 的串行真的不够用时才值得付它的复杂度。**反过来做（先 B）大概率会返工**，因为 B 的调度循环需要 C 的分档表才知道哪些动作能自动派发。
